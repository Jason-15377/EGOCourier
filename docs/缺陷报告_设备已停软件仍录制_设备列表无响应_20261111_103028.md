## 一、缺陷摘要（提单一句话）

配对组参数不一致（主设备 60fps / 从设备 30fps，后演变为 H265 vs H264）。用设备实体键起录时，设备按不一致的录制参数启动了录制，随即上报 `error_flags=0x80000 (recording_aborted)`；**固件侧其实是收到停止后正常收尾、文件已落盘**，但**主机侧 `recording_active` 没有被清除**，界面继续显示"录制中"。同时，设备列表的 `refresh_devices` 请求被长耗时的 `synchronize_connection` 静默拒绝、`group_primary` 恒为空、`DevicePane.qml:1515` 反复写入 undefined，导致**点击设备列表/修改参数无任何响应**。

**用户可见结论：设备上录制已经停了，软件还显示在录；点设备列表改参数，点了没反应。**

### 4.2 设备正常停止，主机状态卡死（核心缺陷）

取最后这一轮（10:29）作为证据：

```
10:29:17.301  主机   physical_capture_requested source=device_button action=route_by_recording_target
10:29:17.317  主机   sd_recording_physical_button_profile_preflight_completed result=mismatch (H265 vs H264)
10:29:22.507  主机   ego_sd_recording_terminated_by_device_error
                      device_id=81c0c32bb0 device_sn=BF8LA60006M
                      terminating_error_flags=0x80000 error_text=ego_state.error.recording_aborted
                      action=clear_host_recording_state_and_stop_group
10:29:22.511  主机   sd_recording_action_started action=stop                          (L6651)
10:29:22.520  主机   sd_recording_operation_completed result=success stop_requested    (L6653)
10:29:22.521  主机   sd_recording_action_completed action=stop result=success          (L6654)
10:29:23.987  主机   transition=recording_started command_sent=false                  (L6659) ← 停止后又"开始"
10:29:23.990  界面   RecordingStartOverlay visible=false（3ms 前刚 visible=true，闪一下）
10:30:16.959  主机   sd_recording_stop_requested                                     ← 37 秒后才补发停止
```

**矛盾一：`command_sent=false`** —— 主机从没下发过起录命令，`recording_started` 全是设备状态回推出来的。

**矛盾二：停止结果被后到的上报覆盖** —— 10:29:22.520 已经"停止成功"，1.5 秒后 10:29:23.987 又把状态推成 `recording_started`。说明状态机**没有"终止锁存优先"**的判定，谁最后上报谁说了算。

**矛盾三（更直白）** —— 10:28 那轮 L6249：

```
sd_recording_ready_ignored device_id=81c0c32bb0 reason=missing_finalization_evidence recording_active=true
```

设备已经 `ready`，主机仍坚持 `recording_active=true`，并且因为"缺 finalization 证据"**拒绝把状态改回 ready**，于是永远卡住。

### 4.3 固件侧证据：录制其实是正常结束的

`firmware/BF8LA60006M/observice.log`：

```
21:29:26.545  ready -> recording      (reason: record_start)
21:30:15.258  recording -> processing (reason: process_start, record data saving)
21:30:16.820  recorders stopped persistence_ok=1 record_complete=0
21:30:16.846  processing -> ready     (reason: record_finish, record finish)
```

`firmware/BF7LA6000KF/observice.log` 同型（10:29:26.545 → 10:30:16.869，同样 `persistence_ok=1 record_complete=0`）。

**结论 A**：设备**没有崩、没有掉盘**，`persistence_ok=1` 表示写卡与元数据同步成功，`record_complete=0` 才是 `0x80000` 的真正来源（录制因参数冲突被收尾，而非硬件故障）。这正是把"参数不一致"错误地包装成"设备异常中断"的地方。

**结论 B**：`error_flags=0x80000` 在 **BF7 固件日志中出现 0 次**，只在 **BF8 出现 1 次**（observice.log:9759）。两台从设备对同一个 abort 的"自述"不对称 —— 主从不一致不只体现在帧率上，也体现在**错误上报路径**上。

**结论 C（关键差异）**：10:06 那轮是 `record_start_failed`（`doStartRecord:2210` 失败、目录被 cleanup 删除、**无文件落盘**）；而 10:28–10:30 这轮是**先起录再正常收尾、文件已落盘**。这两类问题的用户可见现象完全不同，**需要分开修复**：
- 10:06 那轮：`docs/缺陷报告_配对录制帧率不一致导致从设备误报中断.md` 已覆盖（设备侧起录失败）。
- 本轮：**设备侧成功，主机侧状态机卡住** —— 即本报告。

### 4.4 设备列表点击无响应（三条独立证据）

**证据 1｜`refresh_devices` 被互斥静默拒绝**

```
09:28:57.684  device_operation_rejected requested=refresh_devices active=synchronize_connection active_sequence=4  active_age_ms=2
09:30:55.051  ... active_sequence=9  active_age_ms=1
09:32:59.063  ... active_sequence=14 active_age_ms=1
09:38:28.449  ... active_sequence=29 active_age_ms=2
09:42:47.677  ... active_sequence=37 active_age_ms=2
```

而同期 `synchronize_connection` 的耗时是 **4162 / 7570 / 4709 / 4248 ms**（L406、L613、L1026、L1274）。也就是说：用户在 4–7.5 秒的窗口里点"刷新设备列表"，**每一次都在 1–2ms 内被直接丢掉，且界面没有任何提示**。

**证据 2｜配对组信息丢失**

```
23 次  device_list_reordered connected_device_count=1 group_primary=
 1 次  device_list_reordered connected_device_count=2 group_primary=
```

接了 3 台配对设备，设备列表模型却几乎全程认为"只有 1 台连接、主设备为空"。设备项的编辑/修改目标依赖 `group_primary`，**为空 = 编辑目标不存在 = 点了当然没响应**。

**证据 3｜QML 层持续报错**

```
DevicePane.qml:1515:41  Unable to assign [undefined] to QString                    （55 次，另有 24 条同类日志被抑制）
Main.qml:310            TypeError: Value is null and could not be converted to an object（16 次）
Main.qml:437:17         QML GridView: Binding loop detected for property "cellHeight"  （10 次）
```

`DevicePane.qml:1515` 每次都与 `device_selection_changed` 同帧出现（如 10:28:25.971 / 10:28:25.972），即**切设备时把 undefined 写进字段**，绑定失败；`cellHeight` 绑定环让网格反复重算布局，进一步吃掉点击响应。

**因果链**：`recording_active` 卡死 → `synchronize_connection` 长时间占用操作通道 → `refresh_devices` 被拒且无提示 → `group_primary` 为空 + QML 绑定失败 → **点击设备项/修改参数无响应**。

## 五、附带发现（建议另立单，不阻塞本单）

1. **预览时间戳恒定偏移 1.74 秒**（全天 36 次以上）：
   `delta_us=1741372 / tolerance_us=33333`，`consecutive_mismatches=331`。
   偏移是**恒定值**而非抖动，说明是时钟基准未对齐，不是丢帧。疑与参数/时间戳同步同源，建议与 BUG-1/2 一并排查。
2. **`parameter_capability_probe_failed`**（109 次）：`Device Component 'property server' not found`，来自 USB2.0 枚举到的旧设备，属噪声但量大，建议降级为 DEBUG。
3. **主设备电量恒不可读**：`capacity=-1 voltage_uv=0 invalid_reports=12/12`（`72c1a50ee0`）。
4. **录制中改码率被设备拒绝**：`video_encoder_setting_reapply_failed errorCode:7 ... device is streaming or recording to SD card`。属设备正常保护，但 UI 应在录制中禁用这些参数，而不是让用户点了没结果。
5. **网络设备枚举超时**：`VendorTCPClient: Connect to server failed addr=192.168.1.103:8090`。
6. **日志中文乱码**：部分 `detail=` 字段在 WARN 行是乱码（如 L3340），同一内容在 INFO 行正常。建议统一 UTF-8 写出，否则提单时无法直接引用。

## 八、修复优先级建议

1. **BUG-2 + BUG-3（P1，最高）**：状态一致性，影响数据可信度。在 `OrbbecRecordingService` 引入**终止锁存**：`recording_aborted` 置位后，忽略所有 `recording_started`，直到组内全部 ready 且证据齐全；`missing_finalization_evidence` 加超时兜底。
2. **BUG-1（P1）**：把 `physical_button` 与 `host_click` 的 preflight 判定与处置**合并为同一函数**，mismatch 即拒绝，消除行为分叉。
3. **BUG-4 + BUG-5（P1/P2）**：`refresh_devices` 改排队 + 可见提示；`group_primary` 为空时回退到首个在线设备；`synchronize_connection` 加超时。
4. **BUG-6（P2）**：修 `DevicePane.qml:1515` 的空值来源与 `Main.qml:437` 的 `cellHeight` 绑定环。
5. **BUG-7（P2）**：单独排时钟基准，但与 BUG-1/2 同属同步层，建议同一迭代内看。

## 九、结论

> **设备侧是对的，主机侧状态机错了。**

- 设备按参数不一致起录后，因参数冲突自行收尾，**文件正常落盘**（`persistence_ok=1`）；
- 主机把这条正常收尾解析成"设备异常中断"，且停止结果被后到的 `recording_started` 覆盖，`recording_active` 永不落地；
- 卡死的录制状态又让 `synchronize_connection` 长占操作通道、`group_primary` 变空、QML 绑定失败，最终表现为"设备列表点了没反应"；
- 用户可见的"设备已停、软件还在录"与"点设备列表无响应"是**同一条因果链上的两个表现**，不是两个独立 bug。
