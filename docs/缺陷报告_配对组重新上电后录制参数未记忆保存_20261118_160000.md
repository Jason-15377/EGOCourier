## 一、缺陷摘要（提单一句话）

**用户发出的"配对组重新上电后录制参数未记忆保存"，在本次日志里可以拆成两层，结论相反：**

1. **设备侧（已排除）**：SD 录制的设备参数——录制 profile（1096）、切片时长（283）、录制格式（293）、保存到（288）、录制音频（317）——在 15:58:16 下发后，经历 **15:58:51/15:58:56 整组真实断电重启**，回读值与断电前**逐项完全一致**。设备 NVM 没有丢参数。
2. **主机侧（真正缺陷）**：软件没有持久化"配对组/各设备视频流参数（分辨率 / 编码格式 / 帧率）"，也没有在重启或重连后恢复用户上次选择。证据是 15:41:57 正常退出 → 15:55:30 重新打开后，**BF7 彩色从 `1600×1200 · H.265 · 60 fps`、BF8 彩色从 `1600×1200 · H.265 · 30 fps` 双双回落为 `1600×1200 · H.264 · 30 fps`**，全程无提示（§5.2）。整组重新上电重连后，主机同样只能按默认 H.264·30fps 重建流列表（§5.5），随后开流/改流还会把默认值同步写回设备的 1096，覆盖用户之前设置的录制参数（§5.4）。
3. **放大问题**：流参数与设备 SD profile 是联动的——改一次流格式就会改写该设备的 1096（14:54:28 改 BF7 为 H.265，14:54:39 设备 1096 读数即变 HEVC，期间无 `SET 1096`），而且只改一台，导致配对组内 1096 不一致、软件内部 `selected_index=-1`（§5.4）。

**用户可见结论：把配对组调到 H.265 / 60fps 等参数后，只要软件重启或设备重新上电重连，录制相关的视频参数就回到默认 H.264 / 30fps；软件既不提示，也不恢复上次设置；后续开流还会用默认值覆盖设备上已保存的录制 profile。**

## 三、"录制参数"在本软件中的两层含义（先对齐，避免误判）

用户口中的"录制参数"在 2.0.25 里实际分布在两个面板，本报告分别验证：

| 层 | 面板 | 参数 | 存储位置 | 本次结论 |
|---|---|---|---|---|
| **A. 视频流参数** | 数据流（每台设备） | 分辨率、编码格式（H.264/H.265）、帧率（30/60） | **仅主机内存**，`config.json` 无对应字段 | ❌ 未持久化（本单主因） |
| **B. SD 录制设置** | 录制设置（配对组/单设备） | 保存到（288）、录制格式（293）、视频+IMU profile（**1096**）、切片时长（283）、设备保存路径（1097/1098） | 设备 NVM（经协议 SET/GET 回读） | ✅ 设备侧持久化正常；⚠️ 保存路径从未保存（§5.6） |

> 关键点：A 层改动会**联动写入** B 层的 1096（§5.4），所以"用户在数据流里设置的录制参数"最终会落到设备 SD profile；A 层不持久化，就等价于"录制参数记不住"。

## 四、复现步骤

### 4.1 稳定复现（软件重启，本次日志直接可证）

1. 连接配对组（EGO AZEC8640145 + BF7 + BF8），确认 `record_count=3`。
2. 停止预览，在"数据流"中分别设置：
   - BF7（UMI_Finger-L）彩色：`1600 × 1200 · H.265 · 60 fps`
   - BF8（UMI_Finger-R）彩色：`1600 × 1200 · H.265 · 30 fps`
   （本次日志对应 15:13:32 的 frame_rate 变更与 15:14:27 / 15:17:28 的最终状态）
3. 正常关闭 EGOViewer（15:41:55 `Application shutdown started` → 15:41:57 `shutdown completed`）。
4. 重新打开 EGOViewer（15:55:30），连接同一配对组。
5. 观察"数据流"：两台从机彩色均变回 `1600 × 1200 · H.264 · 30 fps`，**无任何提示**。

### 4.2 现场路径（整组重新上电，用户报障场景）

1. 在"数据流"里把配对组视频参数调成非默认值（如 H.265 / 60fps）。
2. 记录"数据流"和"录制设置"两处参数。
3. 整组断电 ≥5 秒后重新上电，等待软件自动重连。
4. 观察：
   - 设备侧 SD 参数（录制格式 / 切片 / 保存到）**保持**（本次已验证，§5.3）；
   - "数据流"中的分辨率 / 格式 / 帧率**回默认 H.264·30fps**（§5.5）；
   - 一旦开流或触发 profile 同步，默认 H.264·30fps 会被写回设备 1096，覆盖用户之前的录制参数（§5.4）。

### 4.3 设备侧持久化对照（排除设备 NVM 问题，1 分钟）

1. 录制设置里把 SD 参数设为 `H.265 · 30 fps / 切片 5 min / 保存到 SD`。
2. 整组断电重启。
3. 回读：master `loadParams: 1600x1300@30 fmt=HEVC seg=5min`；BF7/BF8 `mono 1280x960@30 fmt=HEVC, color 1600x1200@30 fmt=HEVC seg=5min`；`GET 283: 5 min`、`GET 293: mp4`、`GET 288: 0(SD)`、`GET 317: 1`。**全部保留**。

## 六、根因分析（给开发的定位建议）

### 6.1 主机侧（主要责任，用户报障的根本原因）

| 环节 | 现象 | 定位建议 |
|---|---|---|
| 参数持久化 | `config.json` 无"每设备/配对组视频流参数"字段；两个会话间无任何保存动作 | `StreamListModel` / `StreamController` 的 profile 选择状态只存在内存；需要新增按 `device_id + sensor + profile` 的持久化（或在设备端存，但必须能回读） |
| 参数恢复 | 启动/重连后首次 `StreamListModel.cpp:507` 直接是默认 `H.264·30fps`；无恢复/失败事件 | 在设备连接完成（`device_initialization_completed`）后、开流前恢复上次选择；恢复失败要提示，不能静默 |
| 参数覆盖 | 改流格式触发 `recording_profiles_synchronized_to_stopped_streams`，把流参数同步写进设备 1096（`StreamController.cpp:414`、`OrbbecRecordingService` profile 同步逻辑） | 明确"数据流参数"与"SD 录制参数"的联动策略：若要联动，必须整组一致并提示；不能只改一台造成 `selected_index=-1` |
| 用户提示 | 参数被重置/不一致时 UI 无提示 | 增加 `device_parameter_changed_by_device` / `stream_profiles_restored` 事件与 UI 标记 |

### 6.2 设备侧（已排除 NVM 丢失；但有一处实现需固件确认）

- 1096/283/293/288/317 在 15:58:51/15:58:56 冷启动后与断电前完全一致（§5.3），**设备 NVM 正常**。
- 但 14:54:39 BF7 的 1096 读数在没有 `SET 1096` 的情况下随 UVC 编码格式变为 HEVC，说明 `protocol_handle_get_fw_recording_profile`（或 `loadParams`）的取值可能**部分来自当前编码器配置**。请固件确认：
  - 1096 getter 是否直接返回"当前 UVC 编码参数"而非独立存储的 recording profile；
  - 若是，则主机改流参数即等同改录制参数，主机侧必须在改流前确认用户意图，否则"设置录制参数 → 改一次流 → 录制参数被改"无法从设备侧避免。

### 6.3 为什么用户会认为是"重新上电导致"

- 整组重新上电后，设备侧的 SD 参数是保留的（§5.3），但**主机重连后用默认流参数重建 UI**（§5.5）；
- 用户看到的是"数据流/录制设置面板回到默认"，而且一旦开流/触发同步，默认值会写进设备 1096（§5.4），设备上原本保留的用户值也被覆盖；
- 因此"重新上电"只是触发主机重连的时机，**真正的丢失发生在主机侧重启/重连后的默认重建**。

## 九、修复优先级建议

1. **BUG-1（P1）**：为"配对组视频流参数"建立持久化（按 `serial/device_id + sensor + resolution/format/fps`）并在启动/重连后恢复；这是用户报障的直接原因。

4. **固件（P2 咨询项）**：确认 1096 getter 是否直接反映当前 UVC 编码参数；若是，主机侧必须在改流前提示"将同时修改录制参数"。

## 十、结论

> **设备把录制参数记住了；软件没有把"录制参数"记住，而且会用自己的默认值覆盖设备记住的值。**

- 15:58:16 下发的 `H.265 / 30fps / 5min / MP4 / SD / 音频开`，在 15:58:51（从机）与 15:58:56（主机）整组冷启动后回读**逐项一致**——设备端 NVM 正常（§5.3）。
- 15:17:28 → 15:55:57/15:56:29 的直接对照显示：**BF7 的 H.265·60fps、BF8 的 H.265·30fps 在软件重启后全部变为默认 H.264·30fps**；`config.json` 没有这些字段，日志也没有任何恢复事件（§5.2、§5.7）。
- 改一台设备的流格式会静默改写该设备的 1096（14:54:28→14:54:39，无 `SET 1096`），把配对组弄成 `selected_index=-1` 的不一致状态（§5.4）。
- 因此用户所说的"配对组重新上电后录制参数未记忆保存"，**根因在主机侧的参数持久化/恢复缺失，以及流参数对设备录制 profile 的隐式覆盖**；"重新上电"只是让主机重连、按默认值重建 UI 的触发点。

**修复方向明确：主机侧为每设备视频流参数建立持久化并在启动/重连后恢复；把"流参数"与"SD 录制 profile"的联动改为显式、整组一致、有提示；设备侧保持现有 NVM 行为，只需确认 1096 getter 的取值来源。**
