## 一、问题现象

正常录制过程中，主机界面弹出错误提示：

> 录制已停止。设备 BF8LA60006M 上报异常：ego_state.error.recording_aborted
> 检测到设备实体键起录，且配对录制参数不一致：配对组视频流参数不一致：
> BF8LA60006M: 红外: 帧率（主设备 60 fps，设备 30 fps）; BF8LA60006M: 彩色: 帧率（主设备 60 fps，设备 30 fps）;
> BF7LA6000KF: 红外: 帧率（主设备 60 fps，设备 30 fps）; BF7LA6000KF: 彩色: 帧率（主设备 60 fps，设备 30 fps）

但**预览画面全程没有任何卡顿、花屏或断流**，主机侧帧到达率稳定，PTP/时间戳同步统计无异常。

这形成明显的"提示与实际不符"：UI 告知录制异常中断，但用户观察不到任何画面问题。

## 四、根因分析

### 4.1 直接原因（设备侧，已确证）

UMI_Finger-R 的 `Color` 模块**同一时刻只允许一套参数**。预览（UVC owner）与 SD 录制（RECORD owner）请求同一物理 sensor 时，若参数不一致，`onCtrl` 直接返回参数不匹配错误，不降级、不重配：

```c
// observice.log  [Color] [onCtrl:2652]
The camera is already running, but the requested parameters do not match!!
[RecordManager] enable color camera failed
...
[DeviceService] [doStartRecord:2210] record manager start failed, ret=-1
```

此时预览是 **30fps**，SD 录制下发的是 **60fps**，冲突成立 → 三路相机全部 enable 失败 → 录制会话直接失败 → 上报 `recording_aborted`。

**这是设备的正确防御行为**（拒绝在参数不一致时复用已运行的 sensor），不是设备故障。

### 4.2 触发链（为什么会凑出 60 vs 30 的矛盾）

矛盾不是随机的，而是主机侧参数决策逻辑的必然结果：

1. **主机预览按各设备最优选流**：主设备 EGO-4B 支持 1600x1200@60，选 60fps；从设备 UMI_Finger-R 的预览也是 60fps 能力（`sdk_profiles` 里含 `1600x1200 · H265 · 60 fps`）。

2. **配对组参数聚合未做交集**：
   ```
   sd_recording_fixed_resolution_options_aggregated
   saved_profiles=[72c1a50ee0:2=1600x1200·H265·60fps, ..., 81c0c32bb0:0=1600x1200·H265·30fps, 85ef36f0:0=1600x1200·H265·30fps]
   selected_index=-1
   ```
   `selected_index=-1` 表示聚合后没有选出统一的配对参数。聚合逻辑取的是"主设备 resolution/fps 组合"作为配对身份，把 60fps 当成了**主设备期望值**，但**没有把从设备的当前值回写下发**，两边各自保持原状。

3. **实体键起录走了另一条路径**：
   - 主机点击起录 → `sd_recording_firmware_profile_preflight_completed` → mismatch → **拦截**（10:05:13 的行为，正确）；
   - 设备实体键起录 → `sd_recording_physical_button_profile_preflight_completed` → mismatch → **不拦截，继续**（10:06:01 的行为，缺陷）。
   
   两条路径的 preflight 返回值明明都是 `mismatch`，但只有前者执行了 `sd_recording_operation_completed result=failed`。实体键路径把 mismatch 当作"提示"处理，`sd_recording_start_wait_armed` 照常武装并继续向设备下发命令。

4. **设备侧 SD 录制参数 ≠ 预览参数**：
   ```
   [DeviceService] record pipe command: ... fps=60   ← 录制下发 60
   [UVC] configure format: HEVC, 1600 x 1200, fps=30 ← 预览实际 30
   ```
   录制请求没跟随预览的实际运行参数，硬着头皮发 60。

### 4.3 "画面无中断"的解释

这一点**不矛盾**，是必然的：

- **预览走 UVC 通道，全程 30fps 稳定运行**，`Color onCtrl` 的 enable 失败（`enable: 1`）发生在 **RECORD owner** 上，不触碰已在运行的 UVC owner 流；
- 日志中三路相机 `VI-VENC-DIAG` / `OBC-DROP` 在 10:06:08 前后持续输出，说明视频管线未中断；
- 主机 `video_ingress_queue_stats rate_fps=90.x` 稳定、`slow_spans=0`、`queue_bytes=0`，无丢帧堆积；
- 被中断的只是 **SD 录制（写卡）** 这个动作，预览流不受影响。

所以用户体验到的"画面无任何中断"是**符合预期**的：异常发生在录制任务，而非采集链路。

### 4.4 为什么错误提示说"主设备 60fps，设备 30fps"

这条文案本身**方向正确、内容准确**，只是用户容易误读为"设备出故障"。准确含义是：

> 主设备（AZL9861004V / EGO-4B）侧的配对期望是 60fps，但实际运行在从设备（BF8LA60006M、BF7LA6000KF）上的是 30fps。

## 五、责任归属（双端问题，需分别修复）

| 侧 | 问题 | 严重度 |
|---|---|---|
| **主机 EGOViewer** | ① 配对组参数聚合 `selected_index=-1`，未强制对齐主从帧率；② 实体键起录路径的 preflight mismatch **不拦截**，只记录；③ 上报给用户的文案把"参数不一致"包装成"设备上报异常"，误导排障方向 | 主因 |
| **从设备固件** | ① `record pipe command` 下发的 fps 不跟随当前 UVC 运行参数；② `onCtrl` 参数不匹配时直接失败，无自动降级/重配策略（可在冲突时按预览现有参数复用） | 次因 |

**判定：整体为主机侧缺陷（参数协商/预检拦截缺失），固件侧为可改进项。** 从设备拒绝参数不一致的 sensor 复用是合理的防御，不应被视为 bug；但固件可以向主机返回更明确的原因码（区分"参数冲突"与"硬件故障"），便于上层给出正确提示。

## 六、复现步骤

1. 主设备 EGO-4B（AZL9861004V）USB3.2 接入，两台 UMI_Finger-R（BF8LA60006M USB3.2 / BF7LA6000KF Ethernet）作为从设备接入；
2. 在 EGOViewer 中建立 3 设备配对组，启动预览；
3. 确认主设备预览参数为 `1600x1200 H265 60fps`，从设备为 `30fps`（或制造该差异：先让从设备以 30fps 预览，再由主机把目标录制参数设为 60fps）；
4. 按**从设备/主设备的实体录像键**起录（而非主机界面点击"开始录制"）；
5. 观察：约 6.9s 后（10:06:01.659 起录 → 10:06:08.580 报错）主机弹出"录制已停止 / 录制异常中断"，但预览画面无任何异常；
6. 检查从设备 SD 卡：`UMI_Finger-R_BF8LA60006M_20261111_100608` 目录被 cleanup 删除，**无录制文件**。

**对比验证**：同一环境改用主机界面点击"开始录制"，则在 10:05:13 / 10:06:44 / 10:06:55 均被 `recording.sd.preflight_parameters.mismatch` **正确拦截**，不产生误报中断。

## 七、修复建议

### 主机侧（优先）

1. **【必须】配对组参数强制交集**：`sd_recording_fixed_resolution_options_aggregated` 结束后，若 `selected_index=-1` 或成员参数不一致，必须统一解析为所有成员都支持的公共 profile（本例应为 `1600x1200 H265 30fps`），并**下发**到所有成员，而不是仅记录 mismatch。
2. **【必须】实体键起录同样拦截**：`OrbbecRecordingService.cpp:1238` 的 `physical_button` 分支，preflight 为 `mismatch` 时应与 `host_click` 一致，直接拒绝本次起录并给出明确提示（"配对参数不一致，请先在主机侧统一录制参数"），不应继续 `sd_recording_start_wait_armed`。
3. **【建议】统一两条 preflight 路径**：`OrbbecRecordingService.cpp:1307`（physical_button）与 `:3650`（host_click）应共用同一判定与处置逻辑，消除行为分叉。
4. **【建议】修正用户文案**：`recording.sd.terminated_by_device_error` 的 `display_message` 不应写成"设备上报异常"。参数不一致属配置冲突，应区分错误码文案，例如"配对组成员录制参数不一致（主设备 60fps / 设备 30fps），录制已取消"。
5. **【建议】录制参数跟随实际预览**：下发 `record pipe command` 前，用成员实际运行参数覆盖目标参数，确保录制参数 ≡ 预览参数。

### 固件侧（改进）

6. **【建议】`onCtrl` 冲突可降级**：当 RECORD 请求与 UVC 运行参数不一致时，优先按 UVC 现有参数复用 sensor（而非直接 fail），并在日志中显式区分"参数冲突降级"与"硬件错误"。
7. **【建议】返回明确错误码**：`record_start_failed` 时上报区分原因（`param_mismatch` / `storage` / `sensor_dead`），避免上层一律解析为 `recording_aborted`。

## 九、结论

> 这不是录制链路故障，而是**配对组参数协商失败**被以"设备异常"的形式暴露给了用户。

- 预览稳定、画面无中断，属实；
- 中断的是"SD 卡录制"这一个动作，且**真的没有文件落盘**（目录被 cleanup 删除）；
- 触发条件是"实体键起录"，因为主机只在 `host_click` 路径执行 preflight 拦截，`physical_button` 路径漏掉了这一步；
- 根本缺口在主机：配对组聚合未强制对齐帧率（`selected_index=-1`），且未把对齐结果下发到从设备。

修复第 7 节第 1、2 条后，该问题应完全消失；第 6、7 条可显著改善后续排障体验。
