## 一、缺陷摘要（提单一句话）

配对组**没有被解散**，配对组标识 `time=1794362091` 跨重启不变；但主设备 `AZL9861004V` 的配对表在**运行期间**被从 3 条改写成 2 条，且该写入没有任何日志、直到重启才被读出。重启后主设备只能返回 `count=2` 的配对记录，上位机据此判定拓扑无效（`invalid_candidate_topology`），因此**三台设备全部在线、重试 10 次也组不成配对组**。

**用户可见结论：没解散配对组，三台都连上了，但配对组就是不成立。**

## 五、现象与证据

### 5.1 主设备侧：配对表 3 条 → 2 条，且只在运行期被改写

主设备日志 Az 里，总共 64 次 1104（`get_ego_pairing_info`）请求，返回的 `count` 只有两种取值：

```
Az:2660   [09:54:58.233] GET 1104: ego pairing info, state=1 count=3 time=1794362091   ← 唯一一次 count=3
Az:17795  [16:18:34.015] GET 1104: ego pairing info, state=1 count=2 time=1794362091   ← 之后全部 count=2
... 共 63 次 count=2
```

关键的**时间空档**：

| 时间 | 事件 | 配对表读取结果 |
|---|---|---|
| 09:54:58 | 配对组正常工作 | **3** |
| 09:54:58 ～ 16:18:34 | 主设备**连续运行、未重启**，期间 15 次录像起停，但**从未读取过配对表** | — |
| 16:18:34 | 主设备重启（`observice` 重新加载）后第一次读取 | **2** |
| 17:07:22 | 主设备第二次重启 | **2** |

**写入窗口可以进一步收窄到 15:52:42 ～ 16:18:25。** 依据是主设备自身的运行边界：16:18:25.327 出现 `UVC关流`，随后 16:18:33 有一连串时间同步，说明 16:18 才发生服务重启；而 15:52:42.375 之后到 16:18:33 之间，`event.log` 中**没有任何 UVC 开/关流、蓝牙连断、录像起停事件**，即主设备处于空闲运行态。也就是说：

- 15:52:44 上位机还看到 `result=valid member_count=3`（§5.5）；
- 16:18:34 重启后立刻变成 2；
- 中间这 26 分钟里主设备**没有重启、没有读写配对表**，`count` 却已经变了。

这排除了"重启过程中写坏"的可能，指向**运行期某个静默写入路径**。

说明：

- **配对表是在 09:54 之后、16:18 重启之前的运行期被改写成 2 条的**，且窗口可收窄到 15:52:42～16:18:25 的空闲运行态。改写时没有任何日志（整个导出包中**不存在**任何 pairing 的 `set/write/save/persist/update/add/remove` 记录）。
- 改写后一直在内存里生效，因为主设备运行期间不重新读取配对表，所以**问题被"冻结"住了，直到重启才暴露**。
- 这不是"断电丢失"，而是"运行时被写坏、重启后读到的是坏数据"。若真是 NVM 掉电丢失，`time` 也会一起丢，但 `time=1794362091` 完整保留。

### 5.2 主设备角色与参数均正常 —— 排除"变成从机 / 配置损坏"

```
Az:19251  [17:07:22.388] [readDeviceRole] device role: master (/tmp/isslave absent)
Az:19267  [17:07:22.458] initCamParams camparams ready: regenerated=0 fingerprintMatched=1
```

角色仍是 master，camparams 未重建、指纹匹配。说明**只有配对表这一块数据不对**，不是整块配置/身份损坏。

### 5.3 上位机侧：三台都连上，拓扑仍判无效

```
[17:12:34.227] ego_pairing_info_read_completed device_id=72c1a50ee0 record_count=2     (L38)
[17:12:34.241] device_group_derived_from_pairing_info result=unavailable
              pairing_confirmation=invalid_candidate_topology member_count=0           (L39)
[17:12:34.243] ego_pairing_info_retry_started interval_ms=2000 maximum_attempts=10      (L41)
[17:12:54.266] ego_pairing_info_retry_stopped attempt_count=10 reason=attempts_exhausted (L85)
```

四轮会话（17:05:50 / 17:06:03 / 17:07:49 / 17:12:34）**全部**是 `invalid_candidate_topology`、`member_count=0`，从未出现 `secondary_not_connected` 或 `primary_not_connected`。这是一个重要的区分点：

- `secondary_not_connected` / `primary_not_connected` = 设备没连上（15:29、15:49 那几次，见 §5.5）；
- `invalid_candidate_topology` = **设备都连上了，是配对记录本身拼不出拓扑**。

### 5.4 三台设备的记录条数：2 / 2 / 2

17:09～17:12 那次完整接入，三台设备报告如下（同一次会话）：

| 时间 | 设备 | record_count |
|---|---|---|
| 17:09:28.745 | `72c1a50ee0` 主 | **2** |
| 17:09:33.286 | `85ef36f0` 从 L | 2 |
| 17:09:35.172 | `81c0c32bb0` 从 R | 2 |

而正常工作时的形态是 **3 / 2 / 2**（主设备自己 + 两条对端记录；每台从设备只记"自己 + 主设备"一条对端）。即：**主设备少了 1 条对端记录**，从设备侧完全正常。这也解释了为什么从设备都能正常"自报家门"并被连上，唯独拓扑拼不起来。

### 5.5 对照组：同一配对组在当天可以正常重组

排除"该配对组本身有问题"的可能，同一 `time=1794362091` 组在案发前多次正常重组：

```
15:29:51.521  device_group_derived_from_pairing_info result=valid pairing_confirmation=confirmed member_count=3
15:31:56.204  result=valid pairing_confirmation=confirmed member_count=3
15:52:44.348  result=valid pairing_confirmation=confirmed member_count=3
```

且 15:30:40 / 15:49:41 的失败原因是 `secondary_not_connected`（连上慢），而非拓扑无效。**转折点在 16:18 主设备重启**，此后同类操作全部变成 `invalid_candidate_topology`。这是一个干净的 A/B 对照。

### 5.6 从设备侧：配对关系仍在，甚至还在接受新的配对写入

- 两台从设备在 17:08 正常上电、正常广播、正常连上主机（`observice.log` 启动于 09:08，17:08 时间戳正常，无崩溃重启）。
- `BF8LA60006M/ble_wl_provision.log` 在 **17:08:22 又收到并接受了一次配对写入**：

  ```
  17:08:22.088 SE_WRITE: conn_id=4 handle=53 len=22 remote=54:14:FD:25:C8:62
  17:08:22.088 [pair] P001 from 54:14:FD:25:C8:62: accepted
  ```

- 更早在 **同一进程内**，BF8 已经接受过两次配对：

  ```
  s000042_074919.log:20    [14:47:10.052] [pair] P001 from 54:14:FD:25:C8:62: accepted
  s000042_074919.log:1106  [15:33:58.778] [pair] P001 from 54:14:FD:25:C8:62: accepted   ← 同进程第二次
  ```

- BF7 侧同样在 15:17 / 15:24 / 15:31 连续三次接受 `P001`。

即：**配对写入是一条"每次连上就重新下发一次"的重复操作**，从设备每次都"接受"。这正是主设备配对表可能被反复改写的入口，见 §六根因。

## 六、根因分析

### 6.1 根因（主因）：主设备配对表在运行期被改写成 2 条，且无持久化/无日志

结论按证据可分三层：

**第一层：配对表内容错误（已确证）**

同一配对组 `time=1794362091`，主设备从 `count=3` 变成 `count=2`，而从设备始终 `count=2`（正常）。主设备那条多出来的记录是它相对从设备唯一的区别，丢失的正是两条对端记录之一。

**第二层：改写发生在运行期，不是断电丢失（已确证）**

- 重启前后 `time` 一致 → 配对表主体在 NVM 里，没被清空；
- 09:54 读到 3、16:18 重启后读到 2，中间没有任何读取 → 只能是**运行期写入**；
- 16:18 重启后**第一次**读取就是 2，说明写入发生在重启**之前**（窗口 15:52:42～16:18:25，见 §5.1），不是重启流程本身写坏的；
- 整个导出包中**零条** pairing 写入日志（对比：码率、录制格式等参数都有明确的 `SET <id>:` 日志）→ **写入路径没有日志，属于可观测性缺口**。

**第三层：可能与重复配对写入有关（强嫌疑，需固件确认）**

从设备在**同一进程内多次接受 `P001`**（BF8 两次、BF7 三次），且 14:47 与 15:33 之间恰好夹着一次角色错位：

```
15:16:59.705 result=unavailable pairing_confirmation=secondary_not_connected
             member_count=3 member_roles=primary:EGOPro,secondary:UMIFinger,secondary:WristCam
                                                                       ^^^^^^^^^^^^^^
```

如果主体（主设备）对每次"接受配对"都做一次"更新对端记录"的动作，而这些动作之间没有按 `remote_mac` 去重、也没有先删后写，就会表现为"同一台从设备的两条记录互相覆盖 → 净减少 1 条"。**这与"3 → 2"的数值完全吻合，也与"BF8 被重复配对、BF7 被重复配对"的时序吻合。**这一层需要固件侧补充配对表快照日志才能闭环。

### 6.2 加剧因素：上位机把"拓扑无效"当成不可自愈错误，且诊断信息不足

- `ego_pairing_info_retry` 只是**重复读同一份数据**（10 次、2 秒间隔，共 20 秒），**没有任何修复动作**（既不下发配对修复，也不提示用户解散重组）。若主设备配对表已坏，重试 10 次必然是 `attempts_exhausted`。
- 失败时只打印 `member_count=0 member_roles=`，**不打印每台设备的具体记录**（group id / role / remote mac）。故障报告里可见的只有"拓扑无效"四个字，用户和一线支持无法从日志判断是哪条记录丢失。
- 同类问题在 `docs/缺陷报告_重新上电后彩色流参数未记忆保存_20261111_153604.md` §四 已记录 `count=2`，当时被判为"正常"，本次证明它是缺陷前兆。

### 6.3 因果链

```
运行期重复配对写入（从设备多次接受 P001）
        ↓
主设备配对表按 remote 覆盖/追加，净减少 1 条记录（3 → 2）
        ↓（写入无日志、主设备运行期不重读配对表）
问题被冻结，用户无感知
        ↓
三台设备同时断电重启
        ↓
主设备重新加载配对表 → count=2（time 未变，未解散）
        ↓
上位机 device_group_derived_from_pairing_info = invalid_candidate_topology
        ↓（重试只是重读，不修复）
20 秒后 attempts_exhausted，配对组永远组不起来
        ↓
用户表现：没解散、三台都连上、就是组不成组
```

### 6.4 排除项

| 假设 | 结论 | 依据 |
|---|---|---|
| 配对组被解散/清空 | **排除** | `time=1794362091` 跨重启不变；包内无 unpair 日志 |
| 断电导致 NVM 丢失 | **排除** | 同一次重启中码率/录制参数保留，仅配对表变；且时间戳保留 |
| 主设备变成从机/身份损坏 | **排除** | `readDeviceRole: master`、`regenerated=0 fingerprintMatched=1` |
| 从设备没连上 | **排除** | 失败原因是 `invalid_candidate_topology` 而非 `*_not_connected`；三台均有 `device_connect_completed result=success` |
| 服务崩溃/未恢复 | **排除** | 三台 `observice_supervisor.log` 09:08 后无新启动记录；17:08 时间戳正常 |
| USB 枚举/带宽问题 | **排除** | 三台均 `USB3.2` 连接成功，仅拓扑判定失败 |

## 七、预期结果（验收标准）

| # | 预期行为 | 验收方法 |
|---|---|---|
| 1 | 未解散配对组的前提下，三台设备重启后重新连上**必须恢复为 `result=valid member_count=3`** | 反复做"断电→上电→连接"10 次，10 次全部成组 |
| 2 | 主设备 `get_ego_pairing_info` 的 `count` 在配对组建好后**必须恒为 3**，不得因重复连接/重启变化 | 连续 24h 运行 + 多次断连重连，抓 `count` 恒为 3 |
| 3 | 「接受配对写入」**必须幂等**：同一 `remote_mac` 重复接受不得改变配对表条数 | BF8 连续接受 `P001` 3 次后，配对表快照逐字节一致 |
| 4 | 配对表写入**必须有日志**（谁改、改哪条、改前改后条数） | 日志中可见 `pairing_table_write` 类事件；若没有任何写入，则不再出现 `count` 变化 |
| 5 | 上位机在 `invalid_candidate_topology` 时**必须打印每台设备的配对记录明细**，并给出可操作提示（如"主设备配对表不完整 2/3，请解散后重新配对"） | 日志含逐设备 record 明细；UI 出现明确提示 |
| 6 | 上位机的 `ego_pairing_info_retry` **不得在数据不变时机械重试 10 次**；或重试期间同时触发一次配对表修复/重读校验 | 失败时要么修复成功，要么 1 次内明确报错 |

## 八、临时规避（给一线支持）

1. **重新配对**（解散 → 重新配对），不要只重连设备：重连不修复主设备上已存在的错误配对表。
2. 配对过程中**避免在软件里反复断开/连接同一台从设备**，减少重复配对写入的机会。
3. 出现该问题时，从设备日志里应能看到 `[pair] P001 ... accepted` 多次出现（同进程内），可作为现场判断依据。
