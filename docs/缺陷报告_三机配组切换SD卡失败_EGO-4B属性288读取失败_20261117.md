**一句话定位**：三机配组的控制端 EGO-4B（AZLV96100A7 / fw 1.1.11）在主机侧 UVC XU 属性通道失效，`propertyId 288` 读取失败，导致整组切换 SD 卡时被回退为 host；两台 UMI_Finger 的 SD 卡状态正常。

---

## 一、问题现象

三机配组（主设备 EGO-4B + 两台 UMI_Finger）建立后，在录制设置中把“录制位置”切换到 SD 卡：

- 点击切换后界面立即提示：**“无法切换设备录制位置，已恢复原设置。”**
- 09:35:14 至 09:36:13 连续尝试 **9 次，9 次全部失败**。
- 组状态刷新结果为 `result=failed all_host=true all_sd=false ready=false`，界面据此显示整组为“主机录制”。
- 但实际组内两台从设备已经处于 SD 卡录制：`destination=sd_card`，SD 卡容量 119.18 GB、剩余 65.50 GB / 82.22 GB。说明**不是 SD 卡缺失，也不是整组所有设备都不支持 SD 录制**。
- 单独选中 UMI_Finger-L / UMI_Finger-R 时，录制位置均能正常读到 SD 卡；单独选中 EGO-4B 时，录制位置读取失败并被回退为 host。
- 同一时刻 EGO-4B 的视频流、IMU、音频和 `ego_state_report` 均正常，只有属性通道不可用。

**用户影响**：三机配组无法统一切换到 SD 卡录制，录制设置页对 EGO-4B 显示为空能力列表，用户反复点击只能得到同一条失败提示，无法通过 UI 自行恢复。

## 五、定界结论与根因分析

### 5.1 已排除项

| 项目 | 结论 | 依据 |
|---|---|---|
| SD 卡缺失 / 只读 / 空间不足 | 排除 | EGO-4B 的 `/dev/mmcblk1p1` 已 rw 挂载，剩余 67 GB；两台从设备卡也正常 |
| 组内所有设备都不支持 | 排除 | UMI_Finger-L / UMI_Finger-R 均能读到 `destination=sd_card` |
| 配对组配置无效 | 排除 | `pairing_info state=1 record_count=2`，`member_count=3`，`require_all_members_connected=true` 均正常 |
| 协议版本 1 不支持 288 | 排除 | 11/10、11/12 的 protocol v1 主设备均可整组 SD；同一 EGO-4B 在 11/16 也能正常返回 288 |
| 正在预览/录制导致设置被拒 | 排除 | 本次切换请求明确 `streaming=false`；失败点是 `ob_device_get_int_property`，不是 `set` 被设备拒绝 |

### 5.2 失败点

**失败点在主机 ↔ EGO-4B（82aa7089f0 / AZLV96100A7）之间的 UVC XU 属性通道，而不是 SD 卡或配对组本身。**

证据链：

1. 三机配组建组后第一次读取 EGO-4B 组状态（09:34:02.240）就触发 `setXu failed!`（09:34:02.245）。
2. 随后 EGO-4B 的所有属性读取都失败：288、2000、2001、2002、189、2028、279、280、294、317、289 等，参数探测 `available_count=0 failed_count=12`。
3. 09:34:02 首次失败时，EGO-4B 的 4 路视频、IMU、音频仍在正常出流；09:34:11 停止预览后，09:35:06 再次读取 288 仍失败（09:35:14 的切换请求明确 `streaming=false`），排除“流占用导致 XU 忙”。
4. 两台从设备在同一主机、同一时段、同一 USB 拓扑下，288 读取正常，排除主机 USB 栈整体故障。需要说明的是，UMI_Finger-R 在 09:34:13 停止流期间也出现过一次瞬时 XU 失败（18 个参数探测全部失败），但 09:35:03 即恢复并成功读到 `destination=sd_card`；EGO-4B 则是持续性失败，性质不同。
5. 同一 EGO-4B 在 11/16 17:50 还能正常返回 288，说明不是固件“从不支持”。

### 5.3 根因假设（按优先级）

**假设 A（主机侧 SDK / 会话句柄，优先级最高）**
EGO-4B 的 UVC XU 属性句柄在长时间会话、系统休眠/唤醒或设备列表刷新后失效；视频管线通过另一条路径恢复，XU 通道没有重新初始化。SDK 报 `HRESULT 0x8007030e`（系统电源状态转换）而非设备业务错误，符合“句柄/传输层失效”的特征。

**假设 B（EGO-4B 固件属性服务，优先级次之）**
EGO-4B fw 1.1.11 的 DeviceService 属性服务在组状态查询或长时间运行后卡死/异常，导致 XU 响应为空（`Device response size(0)`），但视频与状态上报线程仍存活。需要补充 EGO-4B 的 DeviceService 日志确认。

**假设 C（USB 电源管理 / 端口，优先级较低）**
Windows USB 选择性挂起、Hub 供电或线缆导致该设备的 XU 控制端点进入异常状态；可通过关闭 USB 选择性挂起、换端口/线缆、改用以太网连接做对比验证。

### 5.4 主机侧确定存在的缺陷

无论 A/B/C 哪个成立，主机侧都有明确的可修复缺陷：

1. **单成员失败导致整组回退**：EGO-4B 一个成员读不到 288，整组期望位置回退为 host，UI 显示 `all_host=true`；两台实际仍在 SD 的从设备状态被误报/覆盖。
2. **组状态误报为 all_host**：实际 2/3 在 SD，界面却显示 `all_host=true all_sd=false ready=false`，用户无法判断真实状态。
3. **错误信息不可定位**：统一提示“无法切换设备录制位置，已恢复原设置”，没有指出是 EGO-4B 属性通道无响应，也没有提供“重新连接设备”的建议。
4. **没有自动恢复**：XU 失败后没有重新打开属性句柄或重试；`retryable=false` 让 UI 放弃重试，用户只能反复手点。
5. **QML 状态异常**：`DevicePane.qml:1557: Unable to assign [undefined] to QString` 在组建立、切换设备时反复出现，说明录制位置/状态字段在 QML 模型中为 undefined，可能加重界面显示异常。

### 6.1 前置条件

  - UMI_Finger-L：119.18 GB 卡，剩余 65.50 GB；
  - UMI_Finger-R：119.18 GB 卡，剩余 82.22 GB。
- 主机：Windows x64，USB 3.2 端口直连或经已知稳定的 Hub；记录 USB 选择性挂起设置（本次未记录，复现时需补记）。

## 七、修复建议

### 7.1 主机 / SDK（优先，P1）

1. **XU 属性通道失败可恢复**：捕获 `setXu failed!` / `HRESULT 0x8007030e` / `statusCode 8 + response size 0`，对该设备执行一次属性句柄重开或设备重连，然后重试 288 的 GET/SET；不要直接判定为永久失败。
2. **会话恢复后主动重建属性通道**：在系统休眠唤醒、设备列表刷新、配组 scope 变更后，对所有组成员的属性通道做健康检查；失败则重建，而不是沿用旧句柄。
3. **按成员返回切换结果**：`firmware_recording_destination_update_requested` 应对每个成员分别记录成功/失败；不要因 EGO-4B 一个成员失败就把已经成功的两台从设备回滚到 host。若产品要求“整组一致”，至少要在错误中明确指出失败成员和原因，并提供“重试/重连”入口。
4. **组状态不要默认 all_host**：读取失败的成员应标记为 `unknown`，保留上一次已知的 destination；界面显示“2/3 SD，EGO-4B 状态未知”，而不是 `all_host=true`。
5. **错误分类与文案**：区分 `sd_card_absent`、`sd_card_readonly`、`property_channel_unavailable`、`device_busy` 等；本次应提示“主设备 EGO-4B 属性通道无响应，无法切换 SD 卡，请重新连接设备后重试”。
6. **修复 QML undefined**：`DevicePane.qml:1557` 在 destination/status 为空时应使用明确的占位值（未知/不可用），避免 `Unable to assign [undefined] to QString`。

### 7.2 EGO-4B 固件（P1/P2，与主机并行排查）

7. **审计 288 属性与 XU 服务**：确认 fw 1.1.11 在组状态查询、长时间运行、并发视频流场景下，DeviceService 的属性服务线程不会卡死或返回空响应；为属性服务增加看门狗/自动重启。
8. **补齐设备侧日志**：在 `/tmp/log` 或 `/userdata/runtime/log` 中记录 288 GET/SET、XU 请求/响应、属性服务异常；导出工具应把 EGO-4B 的 DeviceService 日志一并拉取（本次缺失）。
9. **确认 0x20000 含义**：EGO-4B 与 UMI_Finger-R 均上报 `error_flags=0x20000`，但两者的 SD 读取均正常；请固件明确该标志定义，排除与存储/录制位置相关的隐藏状态。
10. **检查 dirty exFAT 处理**：针对 `Volume was not properly unmounted`，确认固件是否会因此进入只读/降级状态；如有，应在挂载后执行 fsck 或明确上报存储错误。

### 7.3 验证与验收

11. 回归矩阵至少覆盖：冷启动 / 长会话（≥8h）/ 休眠唤醒 / USB 重插 / 以太网接入 / 单机与三机 / EGO-4B 作为主设备与从设备（若支持）/ fw 1.1.8 与 1.1.11 / SD 卡正常与缺失。
12. 验收标准：
    - 三机配组切换 SD 卡后，三台成员均回读 `destination=sd_card`，10/10 次成功；
    - 组状态不再出现“2 台在 SD 却显示 all_host”的错误；
    - 单成员属性通道异常时，UI 能指出具体设备并给出可执行的恢复动作；
    - 休眠唤醒、长会话后重复上述用例仍 10/10 通过。
